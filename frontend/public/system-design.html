1. Requirement Understanding

1.1 The Problem in My Own Words

Procurement conducted via ad-hoc emails and disconnected spreadsheets inevitably loses three foundational guarantees: a fair, tamper-proof deadline, an exact like-for-like comparison, and an auditable record of vendor selection. The portal enforces each of these with server-side invariants:

  • Server-authoritative deadline: The deadline is enforced strictly by PostgreSQL's clock timestamp; local device or client time is never trusted.
  • Standardized line-item pricing: Every vendor prices the identical line items defined by the buyer, ensuring quotes align row by row.
  • Append-only audit history: Every status transition is logged immutably, and quote revisions never overwrite previous versions.

1.2 Main Flows per Role

Buyer Workflow:

  1. Sign up and sign in at /login.
  2. Create an RFQ as a Draft: Title, description, category, standardized line items (name, quantity, unit), structured delivery address, optional budget, deadline timestamp, optional PDF/XLSX specifications.
  3. Publish the RFQ. While open, details can be modified; once a vendor submits a quote, line items are permanently locked. After the deadline, no changes are accepted.
  4. Observe bids arrive. Access the comparison view to evaluate bids side-by-side (sort by total price, delivery timeline, or submission order).
  5. After the deadline passes, award exactly one vendor quote. Competing bids transition to REJECTED automatically.

Vendor Workflow:

  1. Sign up and sign in at /login.
  2. Browse active open RFQs (filter by keyword, category, location, and deadline range with pagination).
  3. Open an RFQ detail, download technical specifications, and submit a quote: Unit price per line item, delivery duration in days, notes, and quote files.
  4. Revise the quote as needed prior to the deadline. Each update creates an immutable revision record. Past the deadline, submissions are rejected immediately.
  5. Track quote progression through its lifecycle (Submitted, Shortlisted, Accepted, or Rejected).

Admin Workflow:

  1. Sign in via the dedicated admin portal at /admin/login.
  2. Manage users (activate, deactivate, edit profile), roles, and the dynamic permissions matrix.
  3. Inspect marketplace entities (RFQs, quotes, files, status transitions) in read-only mode, and review the append-only audit log.

1.3 Status Lifecycle State Machines

RFQ State Machine: Draft ──[publish]──▶ Published ──[deadline passes]──▶ Closed ──[award]──▶ Awarded Quote State Machine: Submitted ──[shortlist]──▶ Shortlisted ──[award]──▶ Accepted │ ▲ └──────────────────────────[award]────────────────────┘ Submitted / Shortlisted ──[competing quote awarded]──▶ Rejected

1.4 Scope Boundaries

In Scope: Authentication and per-device sessions, RFQ lifecycle management, quote submission and multi-revision ledger, side-by-side comparison, atomic award transaction with history, file upload verification (magic bytes for PDF/XLSX), search and multi-facet filtering with pagination, relational schema with TypeORM migrations, automated test suite, Docker Compose setup, and a metadata-driven admin panel with RBAC.

Deliberately Out of Scope: Re-opening expired deadlines, quote withdrawals, multi-currency live conversions, complex multi-user corporate organizations, password resets via email, real-time WebSocket streams (HTTP polling utilized), payment checkout, and post-award purchase order execution.

2. Assumptions and Open Questions

To ensure deterministic system behavior under all edge cases, the following 18 architectural decisions were established:

# Question / Edge Case Architectural Decision Justification
1 Can vendors see competing quotes? Strictly No. Vendors only see their own quote. Sealed bids are the essential fairness guarantee of procurement.
2 What happens to previous revisions on update? Preserved immutably in quote_revisions. Ensures full auditability of price changes over time.
3 Can buyers view quotes prior to deadline? Yes, but awarding is disabled until closed. Allows monitoring market response without biasing competition early.
4 Can published RFQs be modified? Yes, until first quote. Line items lock upon first quote. Prevents moving requirements under vendors who already quoted.
5 Whose clock dictates the deadline? PostgreSQL clock_timestamp(). Centralized authoritative clock; immune to client or host drift.
6 When does an RFQ become Closed? Lazy evaluation on read/write plus minute cron. Guarantees second-precise enforcement even if scheduler is delayed.
7 Is Shortlisted mandatory prior to Accepted? No. Direct award permitted from Submitted. Matches procurement workflows when a clear winner is evident.
8 Quote cardinality per vendor? Exactly one quote (UNIQUE(rfq_id, vendor_id)). Modifications create revisions; prevents bid flooding.
9 Outcome for losing quotes upon award? Automatically set to REJECTED atomically. Deterministic terminal lifecycle state recorded in history.
10 Handling of late quote submissions? Immediate 409 DEADLINE_PASSED refusal. No queuing or silent acceptance of bids past the deadline.
11 Monetary calculation format? Integer minor units (paise) stored as bigint. Floating-point arithmetic introduces financial rounding drift.
12 Admin authentication separation? Dedicated admins table with distinct JWT audience. Eliminates privilege escalation risks from public signup.
13 Admin control over marketplace data? Strictly Read-Only. Admins cannot award or modify bids on behalf of buyers.
14 User deletion policy? Deactivation only (soft disable). Historical RFQs and legal bids must retain verifiable owners.
15 Allowed file attachment types? PDF and XLSX, max 10MB, max 10 files per record. Covers RFQ specs and vendor technical proposals securely.
16 Geographic location modeling? Structured: Country, State, City, Pincode. Enables exact multi-facet filtering rather than fuzzy text matches.
17 Can vendors browse expired RFQs? Only if they previously submitted a quote. Vendors access their own archive without cluttering discovery.
18 Email notifications requirement? Best-effort asynchronous (logged if no SMTP). Database operations must never fail due to mail server delays.

4.1 The Three-Layer API Rule

To ensure strict architectural separation and prevent network leakage across UI components, the client enforces a three-tier contract: 

Component (UI) ──▶ services/*.service.ts ──▶ lib/clientApi.ts ──▶ app/api/**/route.ts ──▶ services-api/*.ts ──▶ lib/serverApi.ts ──▶ NestJS
  • lib/baseApi.ts encapsulates fetch logic, query parameter serialization, and error normalization.
  • Single-Flight 401 Interceptor: When an access token expires, clientApi intercepts the 401 response and coordinates a single refresh call. Concurrent 401s coalesce into this single flight; upon token renewal, pending requests replay automatically. If refresh fails, session terminates cleanly.
  • Cookie Isolation: The backend transmits refresh tokens exclusively to the Next.js server, which places them in an HttpOnly; SameSite=Lax; Secure cookie, rendering tokens unreachable to browser JavaScript.

4.2 Dynamic Admin Architecture

A central metadata registry (backend/src/admin/admin-resource.registry.ts) declares all administrative entities once. The system automatically derives permissions, CRUD endpoints, foreign-key lookups, audit logging, and administrative UI tables dynamically.

5. Database Schema and Data Modeling

The schema is managed via TypeORM migrations (backend/src/migrations/1760000000000-InitialSchema.ts). Every statement utilizes IF NOT EXISTS for idempotency. Primary keys are UUIDs, and timestamps use timestamptz.

Table Name Primary Columns Indexes & Integrity Constraints
users id uuid, email, password (bcrypt), role, company_name, phone, is_active UNIQUE(email), CHECK role IN ('BUYER', 'VENDOR')
rfqs id uuid, buyer_id, title, category, budget_minor, deadline, status, awarded_quote_id CHECK status, CHECK budget_minor >= 0, INDEX(buyer_id, status), INDEX(status, deadline)
rfq_line_items id uuid, rfq_id, position, name, quantity numeric(14,3), unit UNIQUE(rfq_id, position), CHECK quantity > 0, ON DELETE CASCADE
quotes id uuid, rfq_id, vendor_id, status, current_revision_no, total_minor, delivery_days UNIQUE(rfq_id, vendor_id), INDEX(rfq_id, total_minor), INDEX(vendor_id)
quote_revisions id uuid, quote_id, revision_no, total_minor, delivery_days, notes UNIQUE(quote_id, revision_no); Immutable append-only
quote_revision_items id uuid, revision_id, line_item_id, unit_price_minor, line_total_minor UNIQUE(revision_id, line_item_id); references line items directly
status_history id uuid, rfq_id, quote_id, from_status, to_status, actor_name, created_at INDEX(rfq_id, created_at); immutable audit ledger
attachments id uuid, rfq_id, quote_id, original_name, stored_name, mime_type CHECK ((rfq_id IS NULL) <> (quote_id IS NULL)), UNIQUE(stored_name)
user_refresh_tokens id uuid, user_id, token_hash, expires_at, is_revoked, user_agent INDEX(user_id); one record per active device session

5.1 Handling of Critical Data Requirements

  • Line Items: Represented as an ordered child table. Quotes reference line items by foreign key, making it impossible to submit pricing for non-existent items.
  • Quote Revisions: The quotes header maintains active totals for fast comparison queries, while quote_revisions and quote_revision_items retain historical snapshots.
  • Status History: Written within the exact same database transaction as the state change.
  • Monetary Precision: All calculations execute in integer minor units (paise). Line Total = ROUND(quantity * unit_price_minor), recomputed on the server to prevent client-side float rounding drift.

7. Key Flows and Concurrency Guarantees

7.1 Quote Submission Prior to Deadline

  1. Vendor submits pricing form via PUT /api/rfqs/:id/my-quote.
  2. The API initializes a database transaction and acquires a shared lock: SELECT ... FROM rfqs WHERE id = $1 FOR SHARE.
  3. Validates PostgreSQL's clock: IF deadline <= clock_timestamp() THEN ROLLBACK & RAISE 409 DEADLINE_PASSED.
  4. Verifies RFQ is PUBLISHED, validates line item IDs, and recomputes line totals on the server.
  5. Locks the vendor's existing quote row (if any). If content changed, inserts quote_revisions record N+1 and updates active totals. If identical, returns current snapshot without redundant writes.
  6. Transaction commits, and an asynchronous notification is dispatched.

7.2 Late Quote Rejection Flow

If a quote arrives when clock_timestamp() >= deadline, the transaction aborts with 409 DEADLINE_PASSED immediately prior to writing any quote records. Existing quotes remain untouched, and the RFQ flips to CLOSED on the next read or scheduler tick.

7.3 Awarding Concurrency Protection

  1. Buyer selects a vendor and triggers POST /api/rfqs/:id/award.
  2. Transaction opens and acquires an exclusive lock: SELECT ... FROM rfqs WHERE id = $1 FOR UPDATE.
  3. Verifies RFQ is CLOSED. If already awarded, immediately returns 409 RFQ_ALREADY_AWARDED.
  4. Updates winning quote to ACCEPTED, all competing quotes to REJECTED, and RFQ to AWARDED atomically.
  5. Writes historical records to status_history for each updated record.

Because submissions take a shared lock and awards take an exclusive lock on the RFQ row, in-flight bids finish before an award proceeds, preventing race conditions.

8. Security and Access Control

Security Vector Implementation Mechanism Threat Mitigated
Sealed Bid Isolation Database queries strictly scoped by vendor_id = caller.id. Competing quotes return 404 Not Found rather than 403. Prevents ID enumeration, competitive price discovery, or competitor bid espionage.
Token Security Access tokens held in JavaScript memory only. Refresh tokens stored in HttpOnly; SameSite=Lax; Secure cookies. Nullifies Cross-Site Scripting (XSS) token exfiltration attacks.
File Validation Magic byte inspection (%PDF- for PDF; ZIP PK header + xl/workbook.xml for XLSX). Random UUID storage names. Prevents disguised executable uploads, path traversal, and file overwrite vulnerabilities.
Admin Isolation Admins reside in a distinct SQL table with dedicated JWT audience tags. User tokens cannot access admin routes. Prevents privilege escalation via token forgery or public registration exploits.
Rate Limiting ThrottlerModule: 10 req/min on authentication endpoints, 300 req/min globally. Constant-time bcrypt comparisons. Prevents brute-force credential stuffing and timing side-channel attacks.

10. Scalability and Next Steps

10.1 Bottlenecks at 100x Scale & Mitigation Plan

Component Bottleneck at 100x Scale Production Architectural Remedy
Session Verification Every API request executes a SQL lookup against user_refresh_tokens. Cache validated session tokens in Redis with 10-minute TTL; evict on logout.
RFQ Search ILIKE '%term%' performs sequential table scans across descriptions. Implement PostgreSQL GIN trigram indexes (pg_trgm) or OpenSearch cluster.
Attachment Storage Local disk volumes saturate under high concurrent upload volume. Transition FileStorageService to AWS S3 / Cloudflare R2 with direct pre-signed URLs.
Database Connections Hundreds of parallel Next.js workers exhaust PostgreSQL connection limits. Deploy PgBouncer for transaction connection pooling and introduce read replicas for comparison queries.

10.2 Roadmap Enhancements

  1. Playwright browser end-to-end user journeys for buyer and vendor personas.
  2. Transactional outbox pattern for guaranteed email delivery with exponential backoff retries.
  3. Structured JSON logging with OpenTelemetry tracing and Prometheus metrics.

Evolution from Initial Design

  • Separation of Admin Identity: Shifted from a user role enum to an isolated admins table with role permissions and dedicated token audiences, preventing privilege escalation.
  • BFF Token Security: Moved refresh token management from browser localStorage to Next.js server-side HttpOnly cookies to eliminate XSS token theft vectors.
  • Flexible RFQ Editing: Refined policy to allow editing descriptions, deadlines, and files of open RFQs until the first quote is received, at which point line items lock permanently.
